# 09/06 — Solutions

Answer key. Every command was run in the container; quoted output is verbatim.

## Warmup

**1.** The numeric entries are one per running process, named for the pid. The non-numeric ones are
kernel-wide: `uptime`, `meminfo`, `cpuinfo`, `loadavg`, `mounts`, `sys/`, and `self` — a symlink to
the reading process's own directory.

**2.** Around fifty entries. None of it is a file in the Chapter 3 sense: nothing is stored, nothing
has blocks, and the "contents" are generated by the kernel when you read.

**3.** Every regular file's size is **0**. There is nothing on disk to measure; the size field is
meaningless for a generated answer.

**4.** `stat -f -c '%T' /proc/<pid>/status` → `proc`. A pseudo-filesystem — the same family as
`/dev` and `/sys`, and not the ext4-shaped thing Chapter 3 described.

**5.** `wc -c` gives **1519** and `cat` prints all of it. The kernel produces the text on demand, and
the number in the listing was never a measurement of it.

## cmdline and environ

**6–7.** The arguments are separated by NUL bytes, which a terminal renders as nothing:
```
0000000   b   a   s   h  \0   b   i   n   /   t   a   g   g   e   d  \0
```

**8.**
```
bash
bin/tagged
300
```
Three arguments, and argument 0 is **`bash`**, not `bin/tagged` — the script is the *first argument*
to the interpreter. This is the same fact that made every script's `comm` equal `bash` in lesson 04.

**9.** `/proc/<pid>/cmdline`, because the NULs are unambiguous. `ps -o args=` joins the arguments with
spaces, so an argument containing a space is indistinguishable from two arguments; `ps` may also
truncate. When the argument list is evidence, read it from `/proc`.

**10–11.** Eight or nine variables for a job started from this shell, including your two:
```
STATION_TEST=abc
PANEL_RUN=deck05
```

**12.** `grep -c PANEL_RUN /proc/<pid>/environ` → **1**. `grep` sees the whole thing as a single line
with no newlines in it, so a "match count" is always 0 or 1 and the matching "line" is the entire
environment. Depending on your grep you may also need `-a`, because NULs make it call the input
binary. Use `tr` first and grep second.

**13.** `-r--------`. Only the owning user, and root. Not the group, not other.

**14.** `sudo cat` works. Reading another account's `environ` as yourself:
`cat: /proc/1234/environ: Permission denied`.

**15.** It does not change. `environ` is the copy the process was handed at exec time; your shell's
export changes your shell, and the running process has its own copy in its own memory.

**16.** Nowhere. It is not written to disk at any point, it is not logged, and it is not recoverable
after the process exits — the memory is freed and there was never another copy. That is the entire
reason the next lesson tells you not to kill anything.

## exe, cwd, root

**17.** `/usr/bin/bash`. Not what you typed: `exe` is the binary being executed, and for a shell
script that is the shell.

**18.**
```
/nix/store/kl3gf8ld3xp638ss3k178r38qn9ywahn-coreutils-full-9.11/bin/coreutils
```
A **multicall binary**: one executable implementing `sleep`, `ls`, `cat` and the rest, choosing
behaviour from argv[0]. So `exe` identifies neither the script you ran nor, here, the command name —
two different reasons, both fatal to "identify it by its executable".

**19–20.** `readlink /proc/<pid>/cwd` on `bin/wanderer`, five seconds apart:
```
/labs/09-processes-and-job-control/06-process-inspection/data/archive
/labs/09-processes-and-job-control/06-process-inspection/notes
/labs/09-processes-and-job-control/06-process-inspection/scratch
```

**21.** `cwd` is a live reading, not a record. It tells you where the process is *now*. An
investigation into what a long-running job has been touching cannot use it as a start-time record —
and a job that moves will give a different answer each time you look, which can be misread as
inconsistency in your own notes.

**22.** `/`. It differs inside a chroot or a container with a different root, and it is one of the
quickest ways to notice that a process is not living in the filesystem you think it is.

**23.** Yes, `cd /proc/<pid>` works and `pwd -P` prints `/proc/<pid>`. When the process exits, the
directory ceases to exist under you: `ls` gives `cannot open directory '.': No such file or
directory` and your shell is standing in a path that is gone.

## Open files

**24.** `0`, `1`, `2` — and `255`, which is bash's own handle on the script it is running. For a job
started from a terminal, 0/1/2 point at `/dev/pts/N`; started from this course's harness they may be
`/dev/null` and pipes.

**25.** Fd 1 (and 2, with `2>&1`) now points at `scratch/out.txt`. The link's own mode carries the
direction: `l-wx` for write-only, `lr-x` for read-only, `lrwx` for read-write.

**26.**
```
l-wx------ 1 cadet cadet 64 ... /proc/10553/fd/9 -> /labs/.../scratch/vanishing.log (deleted)
```
The last word is the whole point.

**27.** `ls` and `find` show nothing, because the *name* is gone from the directory. The bytes are
still allocated, still being written to, and still reachable — through the descriptor.

**28.** `tail -3 /proc/<pid>/fd/9` prints the most recent lines, and printing it again five seconds
later shows more. Opening `/proc/<pid>/fd/9` opens the same **inode** that descriptor refers to; you
are not reading the process's memory, you are reaching the file by a route that does not need a name.

**29.** It works:
```
cp /proc/<pid>/fd/9 scratch/recovered.log
```
Rule: **a deleted file that is still open is not gone; it is unnamed.** The space is released when the
last descriptor closes, so as long as one process holds it you can copy the contents back out.

**30.** `ls -l /proc/<pid>/fd/9` → `No such file or directory`, because the *process* is gone. That is
also the moment the space was freed: the last descriptor closed when the process died.

**31.**
```
COMMAND   PID  USER  FD   TYPE DEVICE SIZE/OFF     NODE NAME
sleep   10451 cadet cwd    DIR   0,73     4096  3288035 /home/cadet
sleep   10451 cadet rtd    DIR   0,73     4096  4108698 /
sleep   10451 cadet txt    REG   0,73  1736976  3016922 /nix/store/...-coreutils-full-9.11/bin/coreutils
sleep   10451 cadet mem    REG   0,73   367708  2127430 /nix/store/...-glibc-2.42-67/lib/locale/C.utf8/LC_CTYPE
```
`cwd` is the working directory, `rtd` the root directory, `txt` the program text, `mem` a mapped file.
None of those four are numbered descriptors — they are things the process has open in other senses.

**32.** Two:
```
bash    10579 cadet 7r   REG   0,73  164 4108845 data/panel-readings.csv
sleep   10585 cadet 7r   REG   0,73  164 4108845 data/panel-readings.csv
```
The second is `sleep` because `bin/reader-of` opened the file on fd 7 with `exec` and then forked a
`sleep`, and **children inherit open descriptors**. The `sleep` never asked for the file and has it
anyway.

**33.**
```
$ fuser data/panel-readings.csv
/labs/.../data/panel-readings.csv: 10579 10585
$ fuser -v data/panel-readings.csv
                     USER        PID ACCESS COMMAND
                     cadet     10579 f.... bash
                     cadet     10585 f.... sleep
```
Paste the `-v` form: it names the user and command. `f` means the process has the file *open* (as
opposed to `c` for it being the process's cwd, `r` for root, `e` for executing, `m` for mapped).

**34.** `lsof -u $USER` selects by the user owning the process; `lsof -c bash` by the command name.
Same distinction as lesson 04: you are selecting processes by an attribute, and the attribute has to
be the one you actually mean. (`lsof` also takes `-u ^user` to exclude.)

**35.** `lsof +D data/` walks the whole tree and stats everything under it — noticeably slower, and it
gets slower with the size of the tree, while `lsof PATH` is a direct question. Use `+D` when you do
not know which file is the problem; never on a large mount.

**36.** `fuser -vm /mount/point` first — it names user, pid and command for everything using the
filesystem, in a form you can read. Then `lsof +D /mount/point` (or `lsof -p <pid>`) when you need to
know *which file* each process is holding. `fuser` answers "who", `lsof` answers "what".

## status and stat

**37.**
```
State:	S (sleeping)
Pid:	10411
PPid:	10395
Uid:	1005	1005	1005	1005
```
Four numbers: real, effective, saved-set and filesystem uid. They differ for a setuid program, and
the effective one is what permission checks use — lesson 04's `-u` versus `-U` again.

**38.** For a background job from an interactive shell, `SigIgn: 0000000000000004` — bit 2, signal 3,
QUIT. `SigCgt` names what the program installed handlers for.

**39.** `Groups:	27 1001 1008` matches `id -G` for a process started by your shell. It would not match
if the process were started by another account, or before a group change.

**40.**
```
$ awk '{print "state="$3" ppid="$4" starttime="$22}' /proc/<pid>/stat
state=S ppid=10505 starttime=295934532
```

**41.** Field 2 is the command in parentheses and it is *not* escaped — a command whose name contains
a space, or a `)`, shifts every field after it. That is why parsing `stat` positionally is fragile and
why anything careful reads from the last `)` rather than from the start, or uses `status` instead.

**42.**
```
Limit                     Soft Limit           Hard Limit           Units
Max cpu time              unlimited            unlimited            seconds
Max file size             unlimited            unlimited            bytes
```
Hitting `Max file size` gives the process `SIGXFSZ` and a write error; hitting `Max open files` gives
`EMFILE` on the next open, which is the usual cause of a long-running service failing hours in.

## nice and renice

**43.** `NI` is **0**.

**44.**
```
  10600  10 bash bin/spin 5
```

**45.**
```
nice: cannot set niceness: Permission denied
rc=0
```
`nice` failed to set the value, printed to stderr, and **ran `true` anyway**, exiting with `true`'s
status. So `$?` after `nice` is the *command's* status and tells you nothing about whether the nice
took. Check `ps -o ni` if it matters.

**46.** `10451 (process ID) old priority 0, new priority 5`.

**47.** `renice: failed to set priority for 10451 (process ID): Permission denied`. The ratchet: a
non-root user may only *increase* niceness, and cannot undo it — not even back to the value it
started at.

**48.** `sudo renice 0 -p <pid>` succeeds. Only root moves in the generous-to-greedy direction.

**49.** It reniced *every* process you own, including your shell and everything it starts afterwards.
Check the blast radius first with `ps -u "$USER" -o pid,ni,args` — or with `pgrep -u "$USER" | wc -l`,
which is the number of processes you are about to change.

**50.** The counts are indistinguishable:
```
spin: 3233 iterations
spin: 3223 iterations
```
`nproc` reports **24**. Two CPU-bound processes on twenty-four CPUs never compete, so niceness never
gets consulted. Niceness only decides who yields *when there is contention*; with none, it is inert.

**51.** Check what the process is waiting for — state `D` or `S` with no CPU time accumulating means
it is blocked on I/O or on something else, and renicing a blocked process changes nothing. `top`'s
CPU% for that process, from lesson 02, is the one-second version of the check.

## Reporting

**52.** In order: `cmdline` (what it was told), `environ` (what it was given), `cwd` (where it is
working), `fd/` (what it has open), and `status` (who it runs as, and its parent). Everything cheap
and non-destructive first; nothing on that list requires touching the process.

**53.** "I can tell you what it was started with, what environment it was handed, which directory it
is working in and which files it has open, all from `/proc/<pid>`. I will collect them in that order,
because the argument list and the environment are the two that identify *which* run this is and the
rest is context. All of it exists only while it runs — the environment in particular is not written
anywhere on disk — so I need it to stay up until I have the capture. After that, killing it costs us
nothing."

**54.**
```bash
p=<pid>; { echo "== cmdline"; tr '\0' '\n' < /proc/$p/cmdline
           echo "== environ"; tr '\0' '\n' < /proc/$p/environ
           echo "== cwd";  readlink /proc/$p/cwd
           echo "== exe";  readlink /proc/$p/exe
           echo "== fd";   ls -l /proc/$p/fd
           echo "== status"; cat /proc/$p/status; } > scratch/pid-$p.capture 2>&1
```
Add `sudo` for a process you do not own — `environ` will be the part that fails without it.

**55.** A real environment routinely contains credentials and tokens, the account and home directory
of whoever started it, internal hostnames and paths that reveal system layout. Redact the values,
keep the variable names; the names alone are usually the evidence.

## Experiment

**56.** It keeps running. `readlink /proc/<pid>/exe` still says `/usr/bin/bash` — unhelpful, because
the interpreter was never deleted. The script is fd 255:
```
lr-x------ 1 cadet cadet 64 ... /proc/18430/fd/255 -> /tmp/v2.sh (deleted)
```
A running program holds an open reference to what it is executing; removing the name does not remove
the inode, and does not interrupt anything.

**57.** Both ends of the pipe show the same inode number in their fd listings:
```
-- 11918 bash bin/tagged 30      1 -> pipe:[22782230]
-- 11919 cat                     0 -> pipe:[22782230]
```
The writer's fd 1 and the reader's fd 0 are the same pipe object. That matching number is how you
prove two processes are connected, which no amount of reading `ps` output will tell you.

**58.**
```bash
whatis-pid() {
  local p=$1
  [ -d "/proc/$p" ] || { echo "no such process: $p" >&2; return 1; }
  printf 'cmdline: %s\n' "$(tr '\0' ' ' < "/proc/$p/cmdline")"
  printf 'cwd:     %s\n' "$(readlink "/proc/$p/cwd" 2>/dev/null || echo '(unreadable)')"
  printf 'exe:     %s\n' "$(readlink "/proc/$p/exe" 2>/dev/null || echo '(unreadable)')"
  printf 'fds:     %s\n' "$(ls "/proc/$p/fd" 2>/dev/null | wc -l)"
  printf 'nice:    %s\n' "$(ps -o ni= -p "$p" | tr -d ' ')"
  printf 'state:   %s\n' "$(awk '/^State:/{print $2, $3}' "/proc/$p/status")"
  printf 'ppid:    %s\n' "$(awk '/^PPid:/{print $2}' "/proc/$p/status")"
}
```
The `-d` test is the graceful exit, and every `readlink` needs its fallback because a process you do
not own gives permission errors rather than absence.

**59.** On pid 1 here: `cmdline` is `sleep infinity`, `ppid` is **0**, and the owner is `cadet`, not
root. All three are odd for an init, and all three match lesson 03: this container's pid 1 is not an
init at all, which is why it never reaps and why the zombies accumulate.

**60.**
```bash
for d in /proc/[0-9]*; do
  t=$(readlink "$d/cwd" 2>/dev/null) && case $t in /labs/*) echo "${d#/proc/} $t";; esac
done
```
You must be able to `readlink` each `cwd`, which means owning the process or being root. You silently
miss every process owned by another account — the `2>/dev/null` is what makes the miss silent, and it
is exactly the blind spot the next lesson is built on.

## Stretch

**61.** Find the holder: `lsof +D /path/to/logs | grep deleted`, or `lsof -p <pid>` if you know it.
Note the fd number. Check free space first (`df`) so you know the copy will fit. Then
`cp /proc/<pid>/fd/<n> /somewhere/with/room/recovered.log` — copy, never move, and never redirect into
the same filesystem you are trying to relieve. The procedure fails completely at step one if somebody
restarts the monitor: the last descriptor closes, the inode is freed, and there is nothing left to
copy. "Try restarting it" is the single most common way this evidence is destroyed.

**62.** Field 22 is the start time in clock ticks since boot. `getconf CLK_TCK` → **100**, and
`/proc/uptime`'s first field is seconds since boot:
```bash
tck=$(getconf CLK_TCK); up=$(cut -d' ' -f1 /proc/uptime)
st=$(awk '{print $22}' /proc/<pid>/stat)
date -d "-$(echo "$up - $st / $tck" | awk '{print $1 - $3}') seconds"
```
You do it the hard way when `ps` is not available, when you are reading a `stat` line captured earlier,
or when you need the value at sub-second precision — and doing it once is how you learn that a
process's age is derived, not stored.

**63.** Run a program that overwrites its own environment (in C, `setenv`; in bash, `export` changes
the shell's copy) and read `/proc/self/environ` before and after. The kernel reports the region of
the process's memory that *was* the initial environment block, so a plain `export` in bash does not
change it, while a program that deliberately rewrites that block does. Conclusion for evidence:
`environ` is strong evidence of what a process was *started* with and weak evidence of what it
believes now. Say which one you mean in a report.

**64.** Disk I/O contention — `ionice`, mentioned in `notes/priority.txt`, plus `iostat`-style
observation of the queue. And memory pressure — swapping, visible as free memory and as the process's
own `VmRSS` in `status`. Both look identical to "slow" from the outside and neither is fixed by
`renice`.

**65.** Answerable without stopping it: pid, ppid, owning uid, start time, nice value, state,
accumulated CPU time, command line, environment, working directory, open files and the contents of
anything it has open. Lost the moment it dies: **environment**, **cwd**, **open descriptors** and the
contents of any deleted-but-open file — plus the ability to ask it anything else you think of later.
Surviving in `ps`-derived form only if you captured it first: everything. Nothing on that list is
written to disk by anybody, which is the whole reason to capture before you signal.
